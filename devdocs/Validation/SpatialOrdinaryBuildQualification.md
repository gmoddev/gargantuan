## Signed package and PlayerGui qualification

The native CLI published and started six FirstCompleteGame distribution profiles and a signed dedicated Server on both ordinary Release platforms. These use the qualification fixture's public Ed25519 test vector and synthetic content key. Linux exercised two builds per profile. The signed, encrypted builds produced distinct manifests and the deterministic profiles produced equal manifests. Windows completed one build per profile. Both exercised all six original negative cases, including missing trust, absent or wrong decryption keys, altered ciphertext, and preservation of a prior package on a failed compile. The retained Windows and Linux signed fixture archives each contain the SignedCompiled Player, Hybrid Player and Hybrid Server. [Profile receipts, manifests, executable and archive digests](SpatialOrdinaryQualification/SignedRuntime.json)

The original optional Python qualification stopped at a private-symbol filename it derived from the manifest alone. The packager had written a destination-scoped sibling and returned its full path. Test-only commit `f355b746a` reads that receipt, matches the sidecar's actual manifest, project, revision, compiler, script path, class and authored source hash, and checks that a copy did not enter the package. One actual-file probe accepted the genuine sidecar and rejected all 14 altered, missing, copied or misplaced cases. The native whole-file package scan ran independently. Two further Windows repetitions received `Access is denied` during the second replacement of a just-started Compiled or Open package. The same replacement error occurred on the stock executable for a Protected package. In each case the preceding on-disk manifest still matched its successful build receipt. The holder of the Windows file handle was not identified. [Fixture correction](../../tests/RuntimeDistributionQualification.py) · [Original failures and before/after digests](SpatialOrdinaryQualification/SignedRuntime.json)

During separate actual GNS joins, each client ran its independent controller and each server ran its own script. Neither client produced the original GUI execution marker. A second authored observer saw the correct LocalPlayer, owned PlayerGui, ScreenGui and child Script on both clients at ticks 1 and 100. Neither client exposed the server script's diagnostic or private source markers. The fixture's original distributed positive assertion remains active.
