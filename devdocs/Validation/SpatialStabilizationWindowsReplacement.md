## Publication contract

The package builder still validates the candidate, declared files, hashes, project, audience and the requested publisher policy before installation. Windows uses an exclusive kernel handle for the destination writer. The handle closes on process termination. Each existing output-parent component is opened directly, checked for reparse attributes and held through cleanup. Each directory move allows up to two seconds for access-denied, sharing and lock errors, with increasing delays capped at 100 ms. A move refuses an existing destination. Cancellation before installation rolls the already moved prior package back.

For replacement, the writer first installs a bounded receipt beside the destination containing the old and new manifest digests. It moves the prior package to the receipt's `old` directory, then moves the validated staging directory into place. A later authorized build verifies the journal, existing contents and admitted package before restoring or retiring it. A crash between the two moves can leave the public output absent until recovery. An unexpected recovery entry is retained and the operation fails. Process termination can leave an uninstalled sibling staging directory or a detached backup. The following publisher leaves unidentified siblings for the owner. Machine power loss and storage write-cache durability are outside the process-crash measurement. [Local publication implementation](../../src/packaging/WindowsPackagePublication.hpp) · [PackageBuilder integration](../../src/packaging/PackageBuilder.cpp) · [Standalone packaging contract](../CurrentArchitecture/StandalonePackagingFoundation1.md)

The CLI now obtains its Windows command-line paths from native wide arguments and passes them to the Engine as UTF-8. The package and package-launch binary formats remain compatible. The installer and updater retain their own signed artifact validation and installed-application lifetimes. This change is confined to publishing the standalone game output that these tools consume.

## Actual process coverage

The Windows regression alternates Development and Release publications to one Unicode path and starts the real Player after each. It times temporary and sustained child-handle contention, validates the prior release, and terminates the real writer while a held staged child prevents its second directory move. A competing operation must fail. After an unknown marker is removed by the fixture owner, a fresh packager restores the exact prior manifest even when a denied runtime file subsequently causes staging to fail. The final package validates and starts from another Unicode directory. A separate nested directory-junction control compares the independent target's contents before and after refusal. [Windows process fixture](../../tests/WindowsPackageReplacement.py)

The early integrated product reached the intentional post-recovery staging failure. The initial observer expected the C++ enum spelling `StageRuntime` while the public diagnostic prints `Stage runtime:`. The revised observer checks the actual error phase and compares the restored manifest independently. The same product accepted an output behind the new test's directory junction before component pinning landed. Both negative results are retained in the qualification evidence.

## Qualified result

The normal Windows x64 Release package builder from `1d9bd6323f855d91da69536cc86f379c952c7410` passed three independent executions of the complete scenario. Each used a new private destination, 12 publish/start cycles, process termination in the two-move interval, recovery and a relocated Player start. The direct executions took 17.922 and 17.047 seconds. The registered CTest took 16.443 seconds. On the receipt-emitting run, the transient hold completed in 0.813 s including process startup, staging and publication. A sustained hold failed in 2.625 s including all package phases. The competing writer failed in 0.062 s. A fresh process restored the exact Development manifest, and the relocated Release manifest matched the original Release digest. [Per-stage timings, manifest and binary hashes](SpatialStabilizationDelivery/WindowsReplacement.json)

Three scripts in the inherited sample lacked persisted source IDs. A matched double-build comparison found exactly three differing source IDs across fresh processes. Persisting those IDs once, as a saved project does, produced identical scene snapshots and retained the regression's strict release-digest equality. The separate Windows runtime-distribution matrix also passed three publication/start repetitions for each of its six package profiles, including signed, protected and hybrid packages.
