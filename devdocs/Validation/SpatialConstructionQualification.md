# Spatial construction production qualification

## Source and execution

The production baseline is `284443879fcecc66a0257006fcdf7d65566fef4d`. A local Git archive of that commit and the existing Windows worker's baseline source archive had the same SHA-256, `fd99294bb08bf6d8f611c12772bf8d764822727a7a0f5c8a93cb891f7ebb0bed`. Each subsequent commit delta is checked against its predecessor before staging. Runtime class code is regenerated with Lute 1.0.0 when generator inputs change. Unchanged generated bytes retain their previous timestamps so Ninja can use normal dependency tracking.

The November 27 worker configurations use separate private source and build directories for each platform. Windows uses x64 Release MSVC 14.51.36231, CMake 3.31.10, Ninja, genuine shaderc, SDL, Box3D, GameNetworkingSockets and SQLite. Only the pre-existing dependency inputs are shared. Windows build concurrency is six. Linux uses Ubuntu 24.04.4, Clang 19.1.1, GCC 14 headers, CMake 3.31.10 and its installed glslc, running headless in a network-disabled three-CPU container with a 6 GiB memory limit. Its private RelWithDebInfo profile enables ASan and UBSan with nonrecovering diagnostics, uses line-table debug information, and disables GNS and the optional serialization benchmark. These profiles run the named project targets and CTest entries. The Linux profile does not reproduce every hosted CI build option.

## Production construction costs

The release worker ran seven alternating grid/Parts trials per layout at `06306967b1c4372aa1a82647709e120a3dab84d6`. The solid occupied all 256 positions in an 8 × 4 × 8 block. The checkerboard occupied alternate positions in a 16 × 1 × 32 region. Both used visible anchored unit cubes, matching occupied coordinates and validated physical hits. Each native grid held one creator Instance. The Parts scenes held 256. Render publication used the CPU publisher and applied the resulting packet. Mesh bytes include vertex and index payloads, and the built-in Part cube already exists in the renderer. This profile measures publication and validated Box3D queries on a worker also running a bounded Linux build. [Benchmark source](../../tests/SpatialConstructionPerformance.cpp) · [28 raw trials](SpatialConstructionBenchmarkBefore.csv)

Values are medians. Each 512-ray batch must return the expected hit, height and owner in all 512 solid rays and the 256 occupied checkerboard rays. The checkerboard grid occupied eight storage leaves. A one-cell deletion republished almost the whole mesh on this revision. The compact solid occupied one leaf. The unchanged publish transferred zero mesh bytes for every case. Native GASM model bytes were 1,902 for solid and 1,753 for checkerboard, compared with 120,461 for either Parts representation. Four release packages built from these pre-edit scenes had identical 24,657,052 runtime bytes each. The normal packager reported project content of 6,517 and 228,617 bytes for solid grid and Parts, and 6,219 and 228,890 for checkerboard grid and Parts. These are matched offline content sizes. The benchmark does not measure packet delivery, dynamic simulation or device frame time.

The same benchmark source ran at `d7868e5faca48ababf981b78165ffc04751bcca6`, after the renderer began retaining vertex ranges for isolated cubes. Removing one checkerboard cell reduced mesh upload from 354,960 to **1,248 bytes** (99.65%) and median CPU publication from 448.6 to **10.7 µs**. The initial model still uploaded 356,352 bytes. The compact case rebuilt 59,392 bytes in 83.3 µs. Parts medians for the same edits were 16.8 µs for checkerboard and 19.2 µs for solid. All four cases again uploaded zero mesh bytes on a pose-only change. Project content bytes were identical to the earlier four packages. The warm 512-ray medians in µs were 482.6 grid and 502.3 Parts on checkerboard, and 415.5 grid and 826.1 Parts on solid. The grid checkerboard first ray was still more expensive at 411.8 µs compared with 42.5 µs for Parts. [28 post-change trials](SpatialConstructionBenchmarkAfter.csv)

A distinct Vulkan oracle deleted one checkerboard cell and restored it with a different tint. Both incremental packets carried 24 vertices and no mesh creation. Each edit changed 528 on-screen pixels. All RGB bytes matched frames generated by a separate publisher and viewport rebuilding the current geometry each time.
