# Standalone application and gameplay lifecycle

**Keep the title screen alive in the Player. Create the gameplay world when the player selects Play.** A creator registers an ordinary `ScreenGui` with `game:SetMainMenu(Menu)`. The same button connections, focus model and menu state can serve two successive worlds. `RunService:PauseGameplay()` requests suspension of the active authoritative simulation. Opening a menu in multiplayer is a separate presentation and input decision.

This is a proposal for an opt-in Player path. Existing packages keep their current startup entry points. The two changes with the largest implementation cost are separating the lifetime of the Player window from Engine teardown and splitting session maintenance from simulation ticks. Neither requires a second creator language or a launcher.

## Registration and application entry

Give the project one optional stable reference, **ApplicationEntry**, selected from existing client-context Scripts. The Script is a direct child of an ordinary Folder under the authored DataModel root. That Folder is the package boundary for the application's screens, assets referenced by the screens, local modules and menu scripts. A creator can also construct controls in Luau. The folder and script may be renamed. Capture their durable authoring identities at the same revision as the world. The package builder must verify an explicit public presentation closure before compiling, protecting or copying it. An application entry cannot reference private server assets, an arbitrary FileLink, a gameplay Instance, a second entry or executable source obtained from a listing. Exclude the designated subtree from ordinary gameplay capture, script discovery, replication and StarterGui provisioning. Existing StarterGui templates continue to serve the per-player HUD.

On explicit app launch, admit package identity, trust and the frozen schema, load the small presentation closure, and execute the selected Script once. Its first bounded, non-yielding turn may call `SetMainMenu`; later GUI handlers may yield through managed application continuations. The last successful registration during that first turn selects the first frame. An entry that returns successfully without a menu takes the existing launch path for its package and arguments. A distributed artifact lacking its required endpoint then reports its existing connection-required result. An invalid declared entry, yield, runtime error or bad closure fails startup explicitly with a bounded diagnostic and a host-owned retry/quit surface. This preserves legacy launch for absent registration without treating a corrupt, opted-in entry as consent to start private gameplay. A developer can invoke retry after a recoverable package-resource failure. The host repeats admission in a new application generation.

`SetMainMenu` accepts one **live app-owned ScreenGui**, including an app-local one constructed at runtime. Registration associates the root with the one app presentation slot. It neither clones it on every show nor reparents a PlayerGui between worlds. Accept only an eligible root within the application graph, validate the entire reachable presentation/reference closure and resource bounds before replacing the old selection. An application can stage multiple screens under its folder, with just the registered root projected. Re-registering the same root succeeds without a second script start. Replacement keeps the slot's visibility, drops stale input targets, releases pointer/IME capture and commits a fresh presentation generation. The old tree remains locally owned until its creator destroys it. Explicit `nil` or destruction clears registration, hides the slot, drops menu input ownership and invalidates queued hit targets. With an active world, the application can register a successor. Idle without a usable menu presents the small recovery surface with retry or quit. The host always handles window close.

Only the entry runs at app bootstrap. Eligible client Scripts beneath a selected menu start once on its first activation. Modules execute via ordinary require in their owning VM. Hidden menus retain state and connections, and receive no UI hits. Their application timers may finish. Replacing or destroying a registered screen cancels its owned outstanding work, disconnects subscriptions and stops its owned sources/voices. A retained deactivated tree can be selected again as a fresh activation with a new execution generation. Entry-owned work persists for the app lifetime. An entry closure that captures an old button must check its activation before acting on it. Application shutdown revokes both kinds of ownership.

**Why this representation.** A live PlayerGui belongs to a Player and retires at disconnect. Keeping a cloned layout alone loses callback closures and interaction state. A second public scene system duplicates binding, rendering, accessibility and asset rules. A native app scope can reuse the existing private DataModel backing, ScriptEngine and GuiRuntime with an explicitly selected projection root. That adds a second internal graph/VM only for the opt-in path. The script sees its ordinary context-local `game`. There is no API for obtaining a second DataModel, assigning LocalPlayer or crossing this boundary with Instances. Quit, session and pause commands cross as checked native values. Restrict app script/service admission explicitly. Giving the application a whole ordinary Offline Engine would bootstrap a Player, default controllers, terrain and gameplay services before Play.

**Presentation and loading.** 2D menus use the existing GUI pass, text, focus, layout, animations and texture pipeline. For a 3D backdrop place a ViewportFrame behind the controls with its own local camera and bounded local models. Its internal camera reference is remapped on initial projection. No current spatial-region reference or gameplay camera is required. A custom menu can animate its camera, transforms, UI tweens or music on application time. Full playable lobby worlds, interactive physics and cross-world camera borrowing exceed this first scope. During joins or loads the same screen can switch panels using operation progress. Keep the last usable UI painted through handshakes. A hidden overlay can leave a live gameplay camera visible beneath it. Viewport running state, capture, listener pose, audio gain and focus all have explicit owners. Restore them only if the target generation is current.

**Visibility at the boundary.** The first successful cold-entry registration selects Visible. If the entry completes without a selection, retire its staging VM/graph and take the existing startup path. Replacing an existing registration preserves its requested visibility. On a running app with a cleared slot, a later registration starts hidden and the creator may explicitly show it. A rejected replacement leaves the previous selection, callbacks and input targets intact. SetMainMenuVisible on an empty slot returns NoMenu. IsMainMenuVisible reports effective presentation, including the root's existing LayerCollector.Enabled state. A rejected or disabled root cannot receive a GUI hit.

## Independent state dimensions

**Native permissions.** The locally admitted application entry and its managed client menu scripts may register/show a menu, claim local input, request sessions, enumerate local saves, use preferences and request a local quit. Required capability, package role, host policy, resource ownership and current execution generation are checked again on Main. A module inherits only its caller's rights. Ordinary session scripts and replicated client code have no application-control grants. World authority alone may read the current save descriptor for gameplay. Edit and PreRun do not dispatch any of these operations. Dedicated servers may receive a separate native administrative pause grant. A future game-to-app “show menu” hint could be opt-in and coalesced; it is outside the initial API.

Input suppression is an idempotent claim per local execution owner. Passing true releases that owner's claim. Effective input also requires a ready world, window focus and absence of other blockers. Suspension, focus loss and teardown clear transient held state. An entry-level owner handles the examples' show and hide actions so they release the same claim.

| Dimension | States / owner | Operation that changes it |
| --- | --- | --- |
| Application | Starting, Running, Closing, Closed · Player or Studio Play sandbox | Admit entry, commit close, retire host |
| Registered menu | Empty, Hidden, Visible · local application | Register/clear, show/hide, destroy |
| Simulation | Absent, Running, Paused · each session's simulation authority | Commit world, first pause holder, final release |
| Session | Idle, Starting, Connecting, Active, Leaving · native session coordinator | Local/host/join admission, handshake, leave/disconnect |
| World readiness | Absent, Preparing, Ready, Retiring · world generation | Attach trusted world and commit its readiness barrier |
| Gameplay input | Available, Suppressed · local dispatcher | Explicit local owner claim, focus/capture loss, world readiness |

Opening a menu changes presentation. Gameplay input routing can be claimed separately. Leaving a world retains the application. Ordinary gameplay pause continues to service app input. Legal examples include Visible + Running + Active (remote overlay), Hidden + Paused + Active (server administration), and Visible + Absent + Connecting (browser with progress). Readiness here describes the local baseline required for gameplay. Streamed regions and later PlayerGui descendants can become available progressively. Each immutable state snapshot carries a session generation and change notifications follow successful commits. Query the current snapshot after subscribing.

## Session commands and failure model

Use one `SessionService` as the Luau façade for lifecycle operations. Existing `Players` remains the owner of gameplay identities, and native `GameSession` retains responsibility for handshake, replication and control. Options and results are bounded values. `SessionService` has no spawn-process, CLI, filesystem path, user ID assignment, credential retrieval or transport-object method. `WorldSaveService` owns the local slot catalog. Its authoritative world descriptor can be read by game code for seed-based initialization.

| From / request | Staging and commit | Failure or repetition |
| --- | --- | --- |
| Idle → StartLocal | Validate profile + save, acquire writer if needed, construct Offline Engine. PrivateServer option starts a trusted local Server and admits only its loopback client. Publish Active/Ready when runtime initialization meets the selected readiness barrier. | Unsupported package topology fails before acquiring a writer. Partial child, provider, runtime and graph retire before Idle. |
| Idle → Host | Select provisioned matching server artifact and storage. Verify policy, open listener, await server readiness, then join it through the normal client path. Advertise only after readiness. | Host with no compatible installed Server returns UnsupportedTopology. Startup timeout or owned child exit withdraws readiness, closes the pair and releases the writer. |
| Idle → Join | Resolve a direct endpoint or native listing handle, validate audience/build, obtain native credentials if required, advance Connecting through authentication, baseline, LocalPlayer/owned GUI binding and required collision/terrain. Attach Engine and advance to Ready before success. | Invalid/expired selection, denial, mismatch, unavailable transport or timeout terminates that attempt and returns to Idle. Preserve the menu and bounded error for retry. |
| Starting/Connecting → Cancel | Cancel the exact operation, invalidate attempt generation, close its transport/child and await teardown. | Repeated cancel returns false after the first accepted cancel. Once the Ready commit wins, Cancel returns false and Leave is available. |
| Active → Leave | Close admission and input, withdraw host listing, quiesce writers and take the save checkpoint required by policy. Retire session and publish Idle. | Concurrent Leave calls observe the same retirement. Leaving while Idle succeeds with Idle. Quit or disconnect can join existing retirement. |
| Active → unexpected disconnect | Fence pending callbacks and ownership, drop projection/control, retain safe reconnect descriptor, emit Leaving then Idle with Disconnected. Show the registered menu on involuntary loss. | An unexpected disconnect never resurrects a player or retries a mutation. In menu-less opt-in flow expose host recovery. Legacy CLI retains its exit behavior. |
| Idle → Reconnect | Use the last eligible endpoint or logical listing, re-resolve and authenticate. Allocate fresh attempt, peer, Player binding, GUI and control epoch. | No descriptor → NotFound. Expired authorization must be reacquired. A listing is advisory. |
| Active → different world | Ordinary workflow awaits Leave before StartLocal, Host or Join. The application remains alive through replacement. | Starting another target while active or busy returns Busy. An aborted destination leaves an actionable Idle menu. No hidden destruction of the old world by Join. |
| Any → application close | Close admission once, cancel uncommitted starts, share session retirement, flush bounded preferences, release presentation and finish. | Repeated Quit/OS close converge. Studio maps Quit to ending this Play runtime. |

Successful Start, Host and Join leave the current screen under creator control, allowing a load-out or ready panel to remain visible. The common flow hides it after success. Leave on its own changes session and readiness. **Return to main menu** is the short composition of showing the registered screen, suppressing local controls and awaiting Leave. Reconnect never reuses opaque gameplay identity. Default manual Leave may retain the prior nonsecret destination until the application closes.

**Operation contract.** Start, Host, Join, Leave, Reconnect, discovery, catalog and pause operations return one host-owned, generation-scoped handle immediately. A denied request can already be terminal. `Await()` returns the latched tagged result, including for an already complete operation. Subscribe to `Completed` for future transitions or use `Await` with a managed yielding continuation. `GetResult()` reads the same outcome. Each operation commits exactly one terminal result. Cancel acknowledges that the operation is still cancellable. Irreversible commit/teardown and pause commands cannot be cancelled after admission. Progress is an optional fraction in [0,1] **within the named phase**. Unknown totals use nil. Coalesce progress per operation per UI frame. Informational messages exclude credentials and raw paths. Errors are ordinary result values. Native programmer misuse (such as a wrong Luau argument type) follows reflection errors.

Order requests and completion publication on Main. Recheck application generation, transition generation, request ID, save revision and presentation generation as applicable immediately before commit and after invoking creator callbacks. Missing/retired owners get no VM resumes. Retire the native resource even if nobody awaits its result. Cancellation is not rollback of a dispatched durable write. Keep bounded operation result snapshots until observation/handle retirement and bound pending waiters. Admission reserves terminal capacity so shutdown and disconnect cannot lose a terminal result. Do blocking I/O and immutable decoding off Main. Replace constructor and handshake polling loops with resumable, budgeted stages wherever UI would otherwise stall.

## Ownership, persistence and application settings

The Player owns the OS window, device/output lifetime, one input pump, one mixer output, the validated package presentation resources and a small local application coordinator. The coordinator holds one optional app graph/VM, one registered menu reference, one active or retiring session generation, one start attempt, and bounded operation/owner registries. A session owns its Engine, world graph/VM, runtime Players, providers and optional local Server controller. A session renderer adapter publishes to the Player compositor. Detaching the adapter fences all its pending frames and forces a new full publication without destroying the window. Generation-scope render handles and texture IDs even where ObjectId bit patterns coincide in two graphs. Associate text focus/capture with the exact displayed frame. On a graphics restart rebuild both projections from authoritative snapshots. On Engine-only restart retire the old session scope and expose an ordinary loss/retry; a Player process restart begins a new app epoch, restoring only committed preferences and catalog entries.

**World slots.** A package is the immutable starting point. Let the native catalog create a stable opaque SaveId (local selectable slot), a WorldId (logical world) and pin ProjectId, compatible package/schema/content version, seed, generator version and committed revision. A duplicate display name is harmless. Preserve seed as a bounded exact string to avoid floating-point truncation. A newly created slot publishes only after its descriptor and initial root are durable. A host reopening it takes the exclusive writer before world creation. A read-only bounded page lists committed compatible or diagnosably incompatible descriptors. Pass a SaveId into StartLocal/Host. Only the authority exposes GetCurrentWorld to world generation code. Joining a remote world grants no access to its owner's slot path or save enumeration.

Use the existing BlockGrid/GAS serialization for supported authored field data and validated checkpoints for game-selected durable records. Store mutable world manifests and sidecars beneath a per-user, per-project save root. Write new data and verify hashes first, atomically replace the manifest/revision last, recover the previous complete root on failure, and retire unreachable blobs after commit. Use single-writer leases, disk quotas, crash recovery and generation-safe flush. DataStore provider semantics remain per-record, including revision compare and uncertain write outcomes. Catalog publication and a complete world checkpoint require an additional local transaction/manifest contract. Define which gameplay entities are durable. Character/control epoch, live PlayerGui, process IDs, session tickets, ObjectIds and pending callbacks are transient. Rebuild them on load from durable references. Persist voxel edits explicitly against the generator/package baseline. Package patches require a compatible migration or return Incompatible before opening a writer.

**Catalog recovery and visibility.** Before accepting a create, reserve a unique operation ID and proposed SaveId in the local profile's durable catalog. Publish a complete descriptor and root atomically. An interrupted or uncertain create returns UnknownOutcome with the opaque RecoveryId when available. ResolveCreate(RecoveryId) examines that original reservation and yields the committed Save, NotFound for a verified abort, or continued uncertainty. Reopen reconciles pending reservations before listing or admitting a conflicting writer. A fresh Create with an identical name/seed is a distinct request. Slot keys are local to the profile. A remote SessionInfo always has nil SaveId; expose WorldId only when deliberately published by authority. An ephemeral local session has no selected slot and GetCurrentWorld returns NotFound.

**Leaving with writes.** Quiesce new writes, temporarily pause as necessary, and drain outstanding operations to a bounded deadline before the irreversible retirement commit. A confirmed checkpoint failure aborts graceful Leave with a typed failure, restores Active/Ready, the writer, prior input and simulation claims and previous eligible advertisement. The user can retry after resolving the cause. An uncertain checkpoint keeps the writer fenced until the catalog reconciles the exact operation and root revision. Explicit Quit or forced shutdown takes precedence over graceful retry, preserves the last confirmed root and records recovery on next boot. Report any lost uncommitted progress through the local UI before a user-initiated forced close. Joining a remote server creates no client-side checkpoint of that server.

**Settings.** ApplicationService owns local close intent, app state and closing notification. It can request quitting the Player or its isolated Studio Play runtime without granting ProcessControl. Keep per-user, per-project bounded scalar preferences with a native profile store outside package and world. InputService/InputContext owns active action maps and rebinding validation. Persist a versioned preference mapping and apply it to each fresh input scope. AudioMixService already owns local gains/mutes; persist chosen gain and reapply it to the shared mixer. DisplaySettings enumerates native-supported opaque display modes. Apply asynchronously, retain a last-known-good mode, and roll back on device rejection or unconfirmed disruptive changes. Headless operation reports Unavailable. Progress belongs to the operation that does the loading. Enumerating saves and choosing one belong to the world catalog and StartLocal/Host respectively.

## Discovery, identity and compatibility

LAN enumeration needs explicit host announcement, a short-lived bounded directory, interface policy and an opt-in local discovery implementation. A resolved row is a hint and confers no admission. Direct join validates a bounded address in the native host and then applies transport security and product policy. Independent authenticated hosting needs its own configured trust/enrollment and credential source. DevelopmentLocal on loopback is an existing mode; public distribution must not silently enable its off-loopback development override. Node-backed discovery can be added behind a configured gateway. Keep Core service registry, private admission/storage and audience secrets unavailable to client code. Exchange opaque listing IDs for native admission bound to the project, exact live server and expected identity. Reconnect obtains a fresh proof. Offline, direct independent, LAN and Node topologies are independently selectable product capabilities.

Deliver mixed-mode games only with an explicit compatible installation profile. A public DistributedPlayer includes public menu code/assets and client projection only. A title offering an authoritative offline world or local host additionally needs the appropriate independently admitted payload and server product on that device. Installation of a server artifact may make its authoritative assets available to that machine's owner; games requiring server-only secrecy must ship only the public join experience. Unsupported options return an explicit error before a world or process is started. DedicatedServer never executes the menu. Keep current CLI flags, no-menu package behavior, source/compiled/protected binding and owner-only PlayerGui behavior. Negotiate any new package or network features by version before activation. An older binary reading an opted-in unsupported format fails clearly. Existing data and old packages need no migration to run directly.
