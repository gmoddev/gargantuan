# Production supervisor prompt

Implement the opt-in standalone Gargantuan game lifecycle in staged, independently reviewable slices. The owner wants a normal runtime ScreenGui registered with `game:SetMainMenu(Menu)`, simple `RunService:PauseGameplay()` / `ResumeGameplay()`, and native local/host/join/leave operations usable from Luau. Begin with the offline title → Play → pause/resume → title → Play → quit loop and a paired legacy direct-launch export.

Read the repository contribution policy, current architecture, relevant accepted designs, invariants and current worktree status. Use the [research report](README.md), [pause contract](Pause.md), [typed candidate](LifecycleTypes.luau), [examples](Examples.md), [evidence](Evidence.md) and [staged gates](Roadmap.md) as design input. The report's pins and retained binaries describe the investigation. Establish fresh exact Engine, Studio, Player, Server and optional Node baselines before modifying production. Check whether parallel spatial/desktop/PreRun/document-editor and authenticated-hosting branches have landed. Work in isolated checkouts. Preserve concurrent changes and their owners' verification gates.

1. Convert the selected ownership/time/authority/package choices into an ADR. Resolve the smallest viable entry representation and package closure against current source. Publish schema and generated typings transactionally through the normal generator. Avoid public source-string execution, raw process controls, a required launcher, a second game GUI, or a second public game root. A private application presentation graph is an implementation choice subject to measurements.
2. Use the existing Player platform pump, ScriptEngine, GUI renderer, asset pipeline, runtime permissions and package audience validation. Keep the opt-in client presentation alive during connection, load, leave and replacement. Give published frames, input targets and operations explicit lifetimes. Keep `StarterGui` / `PlayerGui`, authoritative LocalPlayer binding, workspace/region membership and current GNS readiness intact.
3. Implement and qualify the offline slice first. Control simulation, app presentation and wall-clock services separately. Apply pause at a completed simulation boundary. Test physics, script starts, wait/delay/defer/spawn, synchronous signal waiters, occupied UI input, animation/root motion, tweens, mixer buffers, known/unknown persistence outcomes and graphics restart. Per-owner Pause/Resume and input suppression must survive nesting and owner retirement safely. Use injectable clocks plus real product probes.
4. Introduce world-slot selection and local Server composition only when installed artifacts, writer/recovery, cancellation and shutdown are verified. Implement direct connection first against a supported scope. LAN/Node discovery must preserve independent hosting and no-network offline availability. Authenticate before binding Player or sending credentials. A public client cannot pause or terminate the authoritative server. Only an explicit administrative grant can request a negotiated global pause. A local multiplayer overlay must leave others running.
5. Integrate with the existing outer Studio Play session and Game viewport. App Quit ends only its sandbox. Maintain document revision, editor drafts, debugger behavior and Edit/PreRun/Play boundaries. Provide version-gated Studio controls after coordination with the current development lines.
6. Run the four reference games through actual installed entry points. Include invalid startup, cancel/ready races, stale completions, two-client coverage, disconnect during load and play, repeated start/leave, save-failure recovery, missing provider and package audience denials. Report exact revisions, commands, test receipts, negative controls and resource measurements. Use the repository's remote-worker policy for sustained native builds.

At each stage report shipped surface, observed behavior, unresolved gates and rollback/compatibility behavior. Keep feature availability aligned with tested topology. Do not expose the modeled API as qualified from a research receipt. Do not merge, publish, distribute or modify another campaign's active checkout without separate owner direction.
