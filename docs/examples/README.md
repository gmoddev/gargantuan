# Luau examples

`procedural-world.server.luau` is a Server Script for a fresh world on qualified unreleased spatial candidate `830f5f26ea`. It uses seeded columns, a native bulk grid fill and an optional terrain brush. Terrain editing must be enabled for the brush. See the procedural-generation guide for coordinates, tickets, authority and persistence. Validation is recorded in `devdocs/DocumentationReconstruction/CreatorValidation.md`.

Author these sources through Studio, or place recognized `.luau`, `.client.luau`, and `.server.luau` files in a trusted FileLink source directory for startup-time import. FileLink creates a `ModuleScript` for `.luau` and a `Script` for the context-specific suffixes. It is not a live sync or write API. Set `RunContext` as noted in each script. The examples are parser-checked; only the animation policy has a separate mock-driven Luau behavior test. Each script checks missing setup or recoverable API errors and uses `[System:SubSystem]` diagnostics.

## Play as an authored skinned Character

Import a **skinned glTF Mesh** with `Idle`, `Move`, and action clips sharing its canonical skeleton. Copy the Mesh and Animation references from the asset catalog. Under `ReplicatedStorage`, author a saved `KinematicCharacter` named `PlayableCharacterTemplate`. Give it a `MeshPart` child with that Mesh reference, anchored and non-collidable as in the shipped assembly, and a direct `Animator` child. Set the template's typed `RootPart` reference to that `MeshPart`. Add optional `Attachment` descendants with canonical `JointPath` values. Keep Scripts and other runtime-only, non-Archivable children outside the template; `Instance:Clone()` requires an Archivable subtree and should not duplicate gameplay policy.

Keep the saved `Players.DefaultControllerEnabled`, `DefaultCameraEnabled`, and `CharacterAutoLoads` properties true. The shipped runtime still owns input, movement policy, camera, and the initial spawn. Place `CharacterTemplateAssignment.luau` under `ReplicatedStorage` as a `ModuleScript` and `CharacterTemplateServer.server.luau` as a Server Script. On existing players, new players, and each respawn, that server policy clones the authored template, parents the detached clone to the runtime Workspace, and assigns `Player.Character`. The native setter destroys the previous actor and fires the normal lifecycle signals. The clone remaps its internal `RootPart` reference. A failed clone leaves the current Character in place and logs a bounded warning. Closing the script disconnects its listeners; player removal releases its references.

This setup currently has a brief Part-root Character from the shipped assembler before the server policy replaces it. The client driver ignores that transient actor. A game that needs a different spawn position per player must add its own server spawn policy; this template uses the saved Character CFrame and never writes runtime transforms. `Player.Character` assignment requires server/offline mutation authority and a live Character in the same DataModel, so a Client Script must not perform this replacement.

Studio can author this entirely through the public source and property boundary: create the template, MeshPart, Animator, Modules, and Scripts with `CreateInstance`; use `InitialSource` on Script or ModuleScript creation (or `GetScriptSource` followed by `SetScriptSource` for an existing source); set `Script.RunContext`, `Players` switches, Mesh reference, and typed `Character.RootPart` through schema-backed `SetProperty`; set the reference attributes below with `SetAttribute`; then `SaveProject`. Set `RootPart` with a typed `ObjectReference`, or clear with typed `Null`. The `GetCharacterComposition` inspection can check the saved hierarchy and skeleton paths before Play. FileLink can import the named `.luau`/`.server.luau`/`.client.luau` files at startup, but it is not a live authoring sync path.

## Character animation policy setup

Place `CharacterAnimationPolicy.luau` in `ReplicatedStorage` as a `ModuleScript` named `CharacterAnimationPolicy`. Place `CharacterAnimationDriver.client.luau` as a Client Script. Set its `IdleReference`, `MoveReference`, and `ActionReference` string attributes to three compatible Animation references; `ActionReference` should match the ready clip used by the action scripts below. The driver requires `@game/ReplicatedStorage/CharacterAnimationPolicy`, attaches on `Player.CharacterAdded`, and chooses `Idle` or `Move` from the existing ActionMap movement actions. It chooses `Action` only after `CharacterControlService.ActionResolved` reports server acceptance for `CreatorLunge`, then returns to locomotion on `ActionEnded`. A denied submission or denied action does not select the action clip. Those choices are ordinary game policy; call `Controller:Request(StateName, FadeSeconds)` from your own input, combat, or AI policy for other states. `Policy.New(Animator, RunService, Clips)` accepts one to eight named clip entries. Each entry has `Name`, `Reference`, optional finite `Speed` (0–16), and optional `Looped`. Fades must be finite 0–5 seconds. A new request during a fade starts from the current weights; completion stops the old tracks. Repeating the current request leaves playback alone. `Close()` disconnects the tick and stops every loaded track. A non-looping state remains selected after its natural end until the caller selects another state.

`Animator:LoadAnimation` can fail for missing content, an incompatible skeleton, or the Animator's track capacity. The driver catches construction errors and reports them. The policy has no gameplay movement authority and never enables `AnimationTrack.RootMotionEnabled`.

## Network action and root-motion request setup

The two `CharacterAction` scripts demonstrate a separate authoritative action route. Set the same `AnimationReference` string attribute on both scripts to a ready imported Animation asset, run the server and client contexts in a real session, and integrate the server callback with your **one** game-owned `SetActionPolicy` callback. This standalone server sample installs its own callback and therefore should be adapted if your game already has one. The client binds `F` as `CreatorLunge`; remove or change that binding to fit your ActionMap. Both sides register the same action name, pinned animation reference, 0.5-second duration, and requested 0.9-stud translation. These values are explicit action policy parameters; they are not extracted from clip keys. The native action path evaluates the requested motion through Character authority and collision admission. `RequestAction` returning true means submitted. `ActionResolved` reports server acceptance or denial; neither script sets Character position or treats submission as acceptance. The sample sets `Predictable` to false, so it requests server-authoritative presentation.
