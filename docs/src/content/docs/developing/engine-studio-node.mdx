| Owner | Current responsibility | Boundary |
| --- | --- | --- |
| [Engine](https://github.com/gmoddev/gargantuan) | Authoritative `DataModel`, schema, mutation/history, project persistence, assets, runtime, game networking, and versioned EditorHost | Studio receives DTOs, stable IDs, and pixels, never engine pointers or DataModel authority. |
| [Studio](https://github.com/GantriaEngine/gargantuan-studio) | Editor application, document and source buffers, selection, commands, docking, and presentation | LUI is the primary UI framework; Luau owns workflows, the Host owns windows/processes/IPC/frame lifetimes. ## Authoring path

Studio launches an Engine EditorHost child and negotiates the bounded, versioned local protocol. The Engine opens or creates the project, freezes schema, returns snapshots, then publishes ordered journal changes. Studio reconciles a document projection and submits revision-aware commands; Engine owns the accepted mutation, authoring history, and saved revision. Local Play is an explicit isolated runtime from current in-memory state, with separate scope and identity. See [EditorHost](./editor-host/) and the [Studio owner architecture](https://github.com/GantriaEngine/gargantuan-studio/blob/main/ARCHITECTURE.md).

Script/ModuleScript tabs hold local drafts until `SetScriptSource` commits against the expected `SourceVersion`; text is not a generic replicated property. PreRun is a separate project source with its own revision and validation operations. Project dirty state derives from Engine authoritative versus persisted revision. Engine Undo/Redo traverses engine history and Studio reconciles its journal. Local text Undo/Redo belongs to the one retained native LUI TextBox across dock, move, and float; it does not undo an Engine project action. Asset import, catalog identity, and persistence belong to the Engine project. Studio presents bounded search, dependencies, material details, import/reimport, property asset choices, and preview controls. An asset choice remains local until the Engine accepts the ordinary mutation. The negotiated `AdvancedMaterialMetadata` catalog adds authored material fields where available; it does not certify full renderer feature parity.

Studio also implements explicit single-Script export/import through a receipt bound to Engine-issued `ProjectId`, `SourceId`, and `SourceVersion`. Import previews a candidate before a separate native local edit, and normal Commit Source remains the Engine mutation. This is not a watcher or two-way live synchronization. Engine `SourceMount` separately confines project-relative FileLink and asset-source reads as a startup importer.

The opt-in local development extension platform admits reviewed, capability-filtered effects through isolated fresh workers. Its `SourceWrite` effect edits a retained native TextBox draft with native Undo only after human review; it never calls `SetScriptSource` or bypasses the later explicit Commit Source. Semantic object writes reuse Studio's policy and Engine revision/history path. Project-scoped plugin preferences require a durable `ProjectId` observed through `GetScriptBinding`; an empty project without that binding can remain unavailable. Public **Untrusted** plugin execution is disabled; development isolation does not prove hostile-code containment. Studio's optional authenticated MCP bridge is a different five-method subset: project/selection reads, selection change, Folder/Part creation, and native Name change. It has no Save, Undo/Redo, or script-source authority; the existing MCP consumer may still display unsupported broad-capability tools. See [Studio extensions](https://github.com/GantriaEngine/gargantuan-studio/blob/main/devdocs/AcceptedArchitecture/StudioExtensionsV2.md), [source-edit contract](https://github.com/GantriaEngine/gargantuan-studio/blob/main/devdocs/CurrentArchitecture/StudioPluginSourceEdits.md), and [MCP gateway](https://github.com/GantriaEngine/gargantuan-studio/blob/main/experiments/LuiStudio/McpGateway.md).

The merged Studio tree points to `experiments/LuiStudio` as the active LUI application. Its [architecture](https://github.com/GantriaEngine/gargantuan-studio/blob/main/ARCHITECTURE.md), [LUI document contract](https://github.com/GantriaEngine/gargantuan-studio/blob/main/devdocs/CurrentArchitecture/LuiDocuments.md), and [creator qualification receipt](https://github.com/GantriaEngine/gargantuan-studio/blob/main/devdocs/Validation/StudioCreatorPlatformNativeQualification20261114.json) own exact feature and binary scope. That receipt reports ten accepted gates, including native creator, extension lifecycle, renderer authoring, matched performance, and normal resource retirement. The frozen Avalonia implementation is historical. Physical input, IME, gameplay, broad distribution, and universal latency or memory claims remain outside those bounded native UI journeys. The Studio README retains older pending-gate prose, so use the final receipt and exact source when deciding current status.

## Runtime content path

An official server can choose a local or private Node content provider. Both provide immutable package bytes to the same Engine validation, detached preparation, and authoritative admission path. Content availability does not choose peer relevance or 3J structural publication. The Node [ContentStreaming v1 contract](https://github.com/gmoddev/gargantuan-node/blob/master/docs/content-streaming-v1.md) owns its gRPC method, tenant/capability, filesystem provider, and provider-failure details. Engine owns package identity, residency, live Instances, and downstream networking. See [current networking](./current-networking/) for qualification limits.

## Gameplay persistence path

The Foundation 11 candidate exposes [DataStoreService](../api/networking-and-persistence/#gameplay-datastoreservice) to server scripts. Engine owns request bounds, safe-point delivery, and the public revision and mutation-outcome contract. Studio selects Disabled, Disposable, or Persistent for isolated local Play. Node owns tenant/capability authorization and PostgreSQL transactions in deployed DataStore mode. Use distinct Node tenants for games that require independent storage authority. Development Play never selects a Node credential or packages local profile data. Authenticated Player admission and client package confidentiality have separate delivery gates.
