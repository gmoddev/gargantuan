title: EditorHost and Studio boundary
description: The public process boundary between Gargantuan and the separately authored Studio application.

Gargantuan Studio is a separately authored private application. It consumes
Gargantuan through the public, versioned EditorHost protocol instead of linking
against private engine internals.

The accepted Studio product model is maintained in the private Studio-owned
[Gargantuan Studio Authoring and UX Architecture](https://github.com/GantriaEngine/gargantuan-studio/blob/docs/studio-authoring-ux-architecture/devdocs/AcceptedArchitecture/StudioAuthoringAndUXArchitecture.md).
It defines resource-bound documents, first-party tools, selection, settings and
future TestSession boundaries; acceptance is not feature completion. See the
[public Studio checkpoint](../roadmap/#studio-authoring-checkpoint) for delivered,
planned, architecture-blocked and superseded work. Engine remains the owner of
the protocol, authoritative project, schema, history and persistence.

```text
Private Gargantuan Studio
        |
        | versioned local IPC
        v
Public Gargantuan EditorHost
        |
        v
Mutation Gateway / Snapshot / Journal
        |
        v
Authoritative DataModel
```

The original in-engine Studio prototype was removed after development moved to
this external architecture. Its MPL-2.0-covered implementation remains
available through Git history, but it is not source material for the new Studio
application and must not be copied, adapted, translated, or ported into it.

## EditorHost v0

`SetPropertyBatch` is an optional Engine capability with `PropertyBatchVersion = 1`.
It accepts 1–256 generated prepared-safe property writes, the exact project
revision, and the current snapshot scope. Discovery exposes
`AtomicBatchWritable`; clients must negotiate and use that flag rather than infer
support from datatype. One changed batch is one atomic Engine history action and
revision transition, with normal journal publication and atomic prepared
Undo/Redo. An all-no-op batch changes neither history nor revision. Protocol
version 1 and property-batch version 1 remain unchanged. Schema discovery is now
version 7 for concrete-class defaults when requested with
`GetSchema({ SchemaDiscoveryVersion: 7 })`; parameterless discovery returns
compatible v6. Future reset consumers must opt into v7. Requests over the 1 MiB envelope or
prepared resource budgets reject wholly, without chunking. See the
[canonical request, response, errors and limits](https://github.com/gmoddev/gargantuan/blob/9c4514c1774b07c0ce8b2291147dc60f6a023f3c/devdocs/CurrentArchitecture/EditorHostProtocol.md#prepared-native-property-batches-capability-version-1)
and [qualification receipt](https://github.com/gmoddev/gargantuan/blob/main/devdocs/CurrentArchitecture/PreparedPropertyCommitValidation.md#editorhost-exposure-qualification).
This Engine API does not implement Studio multi-object Properties UX.

Start the headless host with a fresh random token for each launch:

```powershell
gargantuan --editor-host --editor-token <random-token>
```

The client sends bounded, single-line JSON requests over standard input. The
host returns lines prefixed with `GARGANTUAN_EDITOR/1 ` over standard output.
Every request carries protocol version `1`, a request ID, the launch token, a
method, and parameters.

The initial protocol supports:

- protocol handshake and capability discovery;
- project open/creation that runs no gameplay scripts (only bounded PreRun schema registration when configured);
- reflected schema discovery;
- deterministic snapshot capture;
- ordered journal polling; and
- scalar, structural, and bounded script-Source mutation through the authoritative mutation gateway;
- engine-owned project revision state plus atomic Save and Save As;
- engine-owned bounded transactions plus Undo/Redo;
- bounded offscreen RGB viewport capture;
- absolute editor-camera commands; and
- viewport picking that returns a stable `ObjectId`;
- one explicit isolated local Play/Stop lifecycle from current in-memory state; and
- bounded runtime diagnostics and focused key, pointer, wheel, touch, committed
  text, and preedit forwarding.

The optional `PlayInputInspection` capability adds `GetPlayInputSnapshot` for an
exact running `PlaySessionId`, requiring `ReadDataModel`. Its bounded version-1
owning snapshot exposes local contexts/actions/bindings, pressed keys, modifier
masks, conflict/consumption state and cancellation reasons. Runtime scope and
ObjectIds remain separate from authoring identity; this read operation grants no
authoring or server gameplay authority. Clients must capability-gate the method
and discard stale session/scope responses.

The handshake advertises supported viewport transports. On supported Windows
hosts, `LatestFrameMailbox` version 2 with BGRA8 frames is the primary
latest-frame path. Studio negotiates it explicitly; EditorHost owns the mapping
and frame lifetime. `SharedMemoryRing` version 1 with RGB8 frames remains a
compatibility transport with three fixed-capacity slots that overwrite older
frames. Hosts without a shared-memory capability use the bounded Base64
fallback. Clients must select an advertised transport, version, and pixel
format rather than assuming either mapping is available.

Opening a project does not initialize rendering, execute gameplay scripts, step
the simulation, or synchronize `FileLink` objects. Unknown protocol versions,
methods, fields, malformed values, and oversized messages fail closed.
Replacing a project first closes the prior live document and viewport snapshot,
then establishes the next frozen schema before constructing a new DataModel. A
failed replacement leaves no stale world alive against a different registry.

The launch token associates a client with the process. It is sufficient for
the initial local prototype, but it is not strong authentication against a
hostile local user.

## Licensing boundary

Gargantuan, EditorHost, and the protocol remain public MPL-2.0 engine work. The
new Studio repository is private and separately licensed. Studio may launch or
communicate with a Gargantuan build, but it must not copy engine implementation
or depend on private C++ headers.

The shared mapping contains CPU pixel bytes and versioned metadata only. It
never exposes GPU handles, pointers, or renderer objects. Studio validates the
fixed layout, complete state, sequence, dimensions, format, and payload length;
the named mapping disappears when both processes release their session handles.
Picking currently uses BasePart-oriented bounds.

Every viewport transport, configuration, camera, capture, and picking method
requires the explicit `ViewportControl` capability at EditorHost dispatch. The
restricted Studio Luau service receives only viewport size, camera values,
frame sequence/dimensions, and picked stable IDs. Shared-memory names and
handles, RGB buffers, renderer objects, and IPC streams remain in the native
host layer.

The Studio `origin/main` application uses LUI as its primary UI framework.
Luau owns editor workflows and document/buffer policy; the Studio Host owns
windows, process lifecycle, IPC, frame transport, and native resource lifetimes.
See the [cross-repository ownership map](./engine-studio-node/) and the
[Studio-owned current architecture](https://github.com/GantriaEngine/gargantuan-studio/blob/main/ARCHITECTURE.md)
for exact LUI source and qualification pins.
Current Studio supports schema-constrained object-reference editing through
the authoritative property path. Minimal Play sessions are
implemented with a separate runtime DataModel and VM; multiplayer, debugging,
live-edit synchronization, and applying runtime changes back remain deferred.
Structural editing, grouped transactions, Undo/Redo, and dedicated Script/
ModuleScript Source authoring are implemented. Save and Save As persist an
engine-captured project snapshot; Studio never serializes its document cache.
The older Avalonia C# host is frozen historical Studio source, not the primary
application. The public boundary exposes only stable IDs, schema,
snapshot/journal data, structured commands, and viewport pixels. Script domains
(`Core`, `PreRun`, `Studio`, `Server`, and `Client`) are contexts rather than a privilege
ordering; native dispatch authorizes explicit capabilities. Studio's baseline
grant is read access, validated mutation, editor commands, and local selection.
The implemented Luau viewport adapter adds `ViewportControl`; it does not infer
that permission from the `Studio` domain. Process, filesystem, and network
access remain ungranted.

`GetSchema` schema-discovery version 7 exposes the frozen registry generation
and immutable class/enum/extension metadata. Project classes include stable
base and native-host IDs, construction/subclass policy, constructibility, and
ordered declarative properties. Native properties carry datatype and wire type,
effective read/write/editable state, category, optional range and editor hint,
compound identity, exact enum items, and nullable object-reference constraints.
Extension and custom class properties carry the same presentation contract where applicable.
`GetSnapshot` adds `EditorPropertyValuesVersion = 1` and an authoritative
`EditorProperties` projection per object without changing gameplay snapshot v6.
Runtime schema-property edits use `SetExtensionProperty` or `SetCustomProperty`,
snapshot/journal version 6, and the authoritative mutation gateway. Project definitions are created only
by the engine's bounded PreRun candidate lifecycle. Studio receives neither
the `DefineSchema` capability nor the registration facade.

Script Source is saved in the current project Instance format (v5) but is not an ordinary replicated
property. `GetScriptSource` and token-checked `SetScriptSource` require the
trusted EditorHost grant and a live project-scoped ObjectId. Journal/snapshot
traffic carries only the transient SourceVersion invalidation token; source
text does not automatically enter gameplay replication.
