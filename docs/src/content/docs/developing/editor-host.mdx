---
title: EditorHost and Studio boundary
description: The public process boundary between Gargantuan and the separately authored Studio application.
---

Gargantuan Studio is a separately authored private application. It consumes
Gargantuan through the public, versioned EditorHost protocol instead of linking
against private engine internals.

```text
Private Gargantuan Studio
        |
        | versioned local IPC
        v
Public Gargantuan EditorHost
        |
        v
Mutation Gateway / Snapshot / Journal
        |
        v
Authoritative DataModel
```

The original in-engine Studio prototype was removed after development moved to
this external architecture. Its MPL-2.0-covered implementation remains
available through Git history, but it is not source material for the new Studio
application and must not be copied, adapted, translated, or ported into it.

## EditorHost v0

Start the headless host with a fresh random token for each launch:

```powershell
gargantuan --editor-host --editor-token <random-token>
```

The client sends bounded, single-line JSON requests over standard input. The
host returns lines prefixed with `GARGANTUAN_EDITOR/1 ` over standard output.
Every request carries protocol version `1`, a request ID, the launch token, a
method, and parameters.

The initial protocol supports:

- protocol handshake and capability discovery;
- project open that runs no gameplay scripts (only bounded PreRun schema registration when configured);
- reflected schema discovery;
- deterministic snapshot capture;
- ordered journal polling; and
- scalar property mutation through the authoritative mutation gateway;
- bounded offscreen RGB viewport capture;
- absolute editor-camera commands; and
- viewport picking that returns a stable `ObjectId`.

The handshake advertises supported viewport transports. On Windows, Studio can
explicitly negotiate shared-memory ring version 1 for RGB8 frames. The ring has
three fixed-capacity slots; EditorHost overwrites old slots instead of waiting
or growing memory, and Studio consumes the newest complete frame. Platforms
without that capability use the bounded Base64 fallback.

Opening a project does not initialize rendering, execute scripts, step the
simulation, or synchronize `FileLink` objects. Unknown protocol versions,
methods, fields, malformed values, and oversized messages fail closed.

The launch token associates a client with the process. It is sufficient for
the initial local prototype, but it is not strong authentication against a
hostile local user.

## Licensing boundary

Gargantuan, EditorHost, and the protocol remain public MPL-2.0 engine work. The
new Studio repository is private and separately licensed. Studio may launch or
communicate with a Gargantuan build, but it must not copy engine implementation
or depend on private C++ headers.

The shared mapping contains CPU pixel bytes and versioned metadata only. It
never exposes GPU handles, pointers, or renderer objects. Studio validates the
fixed layout, complete state, sequence, dimensions, format, and payload length;
the named mapping disappears when both processes release their session handles.
Picking currently uses BasePart-oriented bounds.

Every viewport transport, configuration, camera, capture, and picking method
requires the explicit `ViewportControl` capability at EditorHost dispatch. The
restricted Studio Luau service receives only viewport size, camera values,
frame sequence/dimensions, and picked stable IDs. Shared-memory names and
handles, RGB buffers, renderer objects, and IPC streams remain in the native
host layer.

The long-term Studio UI is intended to be Luau-authored. A small native shell
will own process lifecycle, IPC, windows, viewport presentation, filesystem
dialogs, and Luau runtime bootstrap. Explorer, Properties, selection, commands,
settings, and most workflows should consume explicit `DocumentService`,
`SelectionService`, `ViewportService`, and `CommandService` APIs from Luau.
Save operations, play sessions, reference-valued editing, and multi-command
transactions remain future interface work.
The current private proof now uses an Avalonia C# host to bootstrap a restricted
Studio-domain Luau VM. The public boundary exposes only stable IDs, schema,
snapshot/journal data, structured commands, and viewport pixels. Script domains
(`Core`, `PreRun`, `Studio`, `Server`, and `Client`) are contexts rather than a privilege
ordering; native dispatch authorizes explicit capabilities. Studio's baseline
grant is read access, validated mutation, editor commands, and local selection.
The implemented Luau viewport adapter adds `ViewportControl`; it does not infer
that permission from the `Studio` domain. Process, filesystem, and network
access remain ungranted.

`GetSchema` schema-discovery version 2 exposes the frozen registry generation
and immutable class/enum metadata. Project enum definitions are created only by
the engine's bounded PreRun candidate lifecycle. Studio receives neither the
`DefineSchema` capability nor the registration facade.
