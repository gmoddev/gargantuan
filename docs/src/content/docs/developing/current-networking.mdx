## State and ownership

The server `DataModel` and its committed `ChangeJournal` are authoritative. `ReplicationCoordinator` turns source state into per-peer semantic operations; it never transfers journal sequence as packet sequence. `NetworkScheduler` admits, prioritizes, bounds, and flushes message intent. `IGameTransport` delivers messages through the deterministic simulator or the pinned GameNetworkingSockets (GNS) adapter. The client `ReplicaApplier` maintains a non-authoritative graph; it has no upstream mutation authority. A peer leaving relevance is unpublished, not destroyed in the source world.

`GameSession` composes the bounded GSES version-1 handshake, negotiated limits, transport connection, replication, Remotes, and Character paths. Connection identity is a generation-safe slot; transport reachability does not identify a Player or authenticate gameplay. Development-local identity is loopback-only by default. The explicit insecure-LAN CLI option is a development override, not authentication. Host-supplied tickets remain separate from decoded payload authority; the current GNS adapter rejects nonempty opaque handshake material pending ticket validation.

The semantic and wire boundaries are distinct. GRPL v1 carries reliable structural baseline and updates; GCHR v4 carries Character realtime state and action results. Remotes use bounded schema-backed event and finite request semantics. Reliable ordering, unreliable best effort, and unreliable sequenced state have different contracts. `Submit` accepts scheduler work, `Flush` offers eligible work to transport, and neither acknowledges remote delivery. Backpressure and disconnect are structured terminal outcomes; remote requests terminate on success, error, timeout, cancellation, or disconnect.

## Peer-specific work

Server relevance combines mandatory and owner-required objects with bounded spatial candidates. Foundation 3K owns generation-safe native spatial projections and cell addresses; 3H uses them for candidate lookup, while relevance and 3J materialization remain separate decisions. 3I stores immutable, revisioned per-object structural descriptions and applies peer-specific reference patches only during publication. 3J schedules dependency-safe, bounded peer enters/leaves and commits Known state only after scheduler acceptance. Character simulation and 20/10/5 Hz peer importance plus age-aware publication do not make structural state authoritative on a client.

Foundation 3L content availability acquires immutable package bytes from a local or optional private Node provider, validates manifest/dependencies/payload, then admits a detached hierarchy through the Engine on Main. `Available` bytes, `Resident` Instances, 3E relevance, and 3J peer materialization are separate states. Node returns bytes to trusted server infrastructure; it cannot allocate `ObjectId`, decide relevance, assign Player identity, or write the live graph. The Node service requires authenticated tenant-bearing node/game-server principals and separate manifest/blob capabilities. See the [Engine 3L contract](../../../../../devdocs/CurrentArchitecture/ContentAvailabilityFoundation3L.md) and [Node owner documentation](https://github.com/gmoddev/gargantuan-node/blob/master/docs/content-streaming-v1.md).

## Qualification boundary

Accepted D03 `POOLED_CORRECTNESS_V1` qualifies the **core correctness contract** at its pinned source. Its timing, service, turnover, and recovery targets are measured nonfatal diagnostics for that contract. This does not rewrite the historical finite-grant/F1 failures. Physical Local32, real-TLS Node32, provider/deployment resource and performance envelopes, and release certification remain **deferred or not measured**. Do not infer a physical F1 PASS or a general Ready state from localhost, simulator, native, or core-correctness results. The integrated main can also lag a 3L working branch; compare exact source and contract identities before carrying a receipt forward.
