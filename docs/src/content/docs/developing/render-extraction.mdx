---
title: Render Publication
description: The immutable incremental-state boundary between Gargantuan's runtime and renderer.
---

Gargantuan renders immutable extracted state:

```text
DataModel / Instances
    -> render-dirty classification
    -> RenderDirtyAccumulator
    -> RenderPublisher
    -> shared_ptr<const RenderPublication>
    -> renderer and render passes
    -> current SDL GPU implementation
```

The governing dependency rule is:

> Renderer/pass code consumes immutable extracted state and does not traverse
> the DataModel.

## Publication contract

A `RenderPublication` owns its sequence/base identity, viewport/camera/light
state, deterministic object creates/updates/removes, dynamic mesh lifecycle and
dirty ranges, a complete immutable UI frame when UI changed, and diagnostics.
The UI frame may be shared as `shared_ptr<const RenderUiFrame>` through publisher
and projection to avoid repeated geometry copies. An absent UI update preserves
the current projection; an explicit empty frame clears it. Render values contain only
stable generational identities, logical geometry, transforms, materials,
visibility, and shadows.

Publications contain no Instance, WorldRoot, Camera, callback, or runtime-owned
container pointers. They are published as const shared ownership, so later
runtime mutation or destruction cannot change or invalidate a frame already
being rendered.

The renderer applies each publication atomically to a disposable persistent
projection. Incremental bases must be exact; a full-resync publication can
reconstruct that projection independently. The same projected `ObjectId` is
used for viewport picking. Normal `ObjectRegistry` lookup rejects an identity
whose generation is stale.

## Dirty accumulation and coalescing

Committed authoritative mutations are classified into transform, material,
visibility, geometry, deformable, and hierarchy/render-presence domains. One
bounded accumulator entry exists per dirty `ObjectId`, regardless of how many
times a property was written. Publication reads only the final authoritative
state: repeated writes become one update, create plus updates becomes one final
create, create plus destroy disappears, and update plus destroy becomes remove.
Irrelevant properties do not dirty rendering.

Accumulator capture is retried until a complete publication is successfully
constructed and acknowledged. Hard limits bound scopes, live consumers, distinct identities,
deformable bytes, UI bytes, publication bytes, and diagnostics. Limit failure
requests an exceptional full resync; it never emits a partial delta. The
general `ChangeJournal` remains independently bounded and is not the renderer's
volume queue.

## Timing and identity

The runtime publishes after simulation and `PreRender`, immediately before its
draw call. EditorHost uses a separate accumulator consumer and publisher for
offscreen capture. It keeps a CPU-only projection of those same publications
for picking, so selection remains headless and never requires GPU startup.

Publication currently runs on the authoritative Main domain and rendering is
synchronous. The value-only publication contract is suitable for later
main-to-render-thread publication, but this pass does not add a render thread.

Publication identity is a session-local unsigned 64-bit sequence. Zero is
invalid, the first successful publication is 1, and exhaustion fails instead of
wrapping. Incremental values name their exact base. It is separate from
`ObjectId`, schema generation, journal sequence, and viewport presentation
frame numbers.

## Camera and resources

Runtime Camera Instances and EditorHost's plain camera state both become one
`RenderCameraInput`. View, projection, and view-projection matrices are derived
during extraction; passes never read a Camera Instance.

Parts expose logical `PartType`, not `GpuMesh`. Each SDL renderer owns a
device-local primitive/dynamic mesh cache and resolves the publication's
`RenderGeometry` and mesh identities below the boundary. Dynamic topology is
uploaded once and stable-topology deformable publications update only the
validated vertex range.

Fatal world/camera/viewport errors reject the whole candidate publication.
Individual invalid items are skipped with explicit extraction diagnostics.
Unavailable GPU primitive resources are reported and skipped by the renderer.

## Backend resource boundary

SDL GPU types are confined to the current backend implementation and its
private helpers. Public/general render headers, `BaseRenderer`, `Mesh`, and the
EditorViewport semantic contract expose no SDL GPU handles. This boundary does
not introduce `RenderDevice`, a generic graphics API, backend selection, or
render threading. Foundation 2C adds renderer-neutral material/texture
lifecycle values and an SDL-private GUI pipeline with persistent buffers,
scissors, alpha blending, and atlas sampling. See
`devdocs/CurrentArchitecture/RendererBackendBoundary.md` for the verified
ownership and leakage audit.

The hard soft-body flow is solver-owned simulation to engine-owned deformable
render values to `RenderDirtyAccumulator` and immutable `RenderPublication`,
then a renderer-owned persistent mesh. Physics solver objects and writable raw
solver memory never cross the seam. The first producer is now the sibling CPU
XPBD cloth/rubber backend documented in
[`SoftBodyPhysicsFoundation.md`](../../../../../devdocs/CurrentArchitecture/SoftBodyPhysicsFoundation.md).

## Renderer technology decision checkpoint

This section is non-normative future guidance. Gargantuan should revisit its
renderer technology before the "competent lighting/renderer" roadmap work grows
into a mature material, asset, lighting, culling, batching, and post-processing
stack. The decision should be driven by a measured comparative prototype, not by
making the current SDL implementation permanent by default.

The candidate directions are:

1. Gargantuan owns engine and rendering semantics while Filament supplies most
   rendering technology.
2. Gargantuan owns engine semantics while Ogre-Next owns a disposable,
   persistent render-side scene projection.
3. Gargantuan owns both engine semantics and a renderer built on a lower-level
   API such as Diligent or SDL GPU.

The first investigation should introduce only the smallest internal backend
seam needed to compare one serious alternative, initially Filament, with the
current SDL path. It should not build three polished backends. Compare at least
material flexibility, instancing and batching, culling, lighting, large-scene
performance, platform support, integration cost, debugging, licensing, and
EditorHost compatibility. If rendering behavior proves to be a product
differentiator that an integrated renderer cannot express without distorting
Gargantuan's model, that evidence can justify owning more of the stack.

Every option must preserve the existing authority boundary:

```text
authoritative DataModel
    -> extracted or incrementally maintained render projection
    -> immutable publication
    -> renderer-owned scene and GPU resources
```

Renderer Foundation 2B uses incremental immutable publication in the supported
runtime and EditorViewport. `RenderSnapshot` remains compatibility/full-state
scaffolding, not the normal renderer path. See
[`RendererFoundation2.md`](../../../../../devdocs/CurrentArchitecture/RendererFoundation2.md)
for the accepted delta/full-resync contract, deformable and GUI boundaries,
benchmarks, backend decision, and bounded migration sequence.

Foundation 2C selected SDL GPU after real 300-frame fence-complete and
1,800-frame queued deformable/GUI tests on AMD and NVIDIA hardware. It
authorizes the GUI runtime to publish engine-owned layout/text/atlas results as
`RenderTexture` lifecycle plus complete `RenderUiFrame` values. GUI Foundation 2
retains that renderer-neutral contract and adds shared immutable ownership rather
than a speculative UI delta. See
[`RendererFoundation2C.md`](../../../../../devdocs/CurrentArchitecture/RendererFoundation2C.md).

Any persistent render scene is a disposable `ObjectId`-indexed projection, not
game state. It never becomes authoritative or retains live `Instance` pointers.

Renderer benchmarks must also separate GPU rendering from Studio viewport
presentation. GPU-to-CPU readback, pixel conversion, shared-memory transfer,
managed copies, and bitmap upload can dominate observed Studio frame time
independently of the renderer. Measure these stages separately. A shared GPU
texture may later become the preferred fast path, while the bounded RGB
shared-memory transport remains a portable fallback; adopting such a path
requires its own process-boundary and lifecycle review.
