---
title: Render Extraction
description: The immutable frame-state boundary between Gargantuan's runtime and SDL renderer.
---

Gargantuan renders immutable extracted state:

```text
DataModel / Instances
    -> RenderExtractor
    -> shared_ptr<const RenderSnapshot>
    -> renderer and render passes
    -> current SDL GPU implementation
```

The governing dependency rule is:

> Renderer/pass code consumes immutable extracted state and does not traverse
> the DataModel.

## Snapshot contract

A `RenderSnapshot` owns its extraction identity, viewport dimensions, complete
camera matrices and directions, lighting direction, render items, and
extraction diagnostics. A render item contains only stable `ObjectId`, logical
primitive geometry, transform/inverse transform, color/opacity, and its current
shadow flag.

Snapshots contain no Instance, WorldRoot, Camera, callback, or runtime-owned
container pointers. They are published as const shared ownership, so later
runtime mutation or destruction cannot change or invalidate a frame already
being rendered.

Items are ordered by `ObjectId`. The same identity is used for frame-local
viewport picking. If an object is destroyed after extraction, the displayed
snapshot remains internally valid while normal `ObjectRegistry` lookup rejects
the stale ID; the next extraction omits it.

## Timing and identity

The runtime extracts after simulation and `PreRender`, immediately before its
draw call. EditorHost extracts on viewport capture and uses the same snapshot
for offscreen rendering. Picking uses the displayed snapshot when one exists.

Extraction currently runs on the authoritative Main domain and rendering is
synchronous. The value-only snapshot contract is suitable for later
main-to-render-thread publication, but this pass does not add a render thread.

Snapshot identity is a session-local unsigned 64-bit extraction sequence. Zero
is invalid, the first successful extraction is 1, fatal failures do not consume
a value, and exhaustion fails instead of wrapping. It is separate from
`ObjectId`, schema generation, journal cursor, and viewport presentation frame
numbers.

## Camera and resources

Runtime Camera Instances and EditorHost's plain camera state both become one
`RenderCameraInput`. View, projection, and view-projection matrices are derived
during extraction; passes never read a Camera Instance.

Parts expose logical `PartType`, not `GpuMesh`. Each SDL renderer owns a
device-local primitive mesh cache and resolves the snapshot's `RenderGeometry`
keys below the extraction boundary. This preserves current primitive behavior
without introducing an asset or general resource system.

Fatal world/camera/viewport errors reject the whole candidate snapshot.
Individual invalid items are skipped with explicit snapshot diagnostics.
Unavailable GPU primitive resources are reported and skipped by the renderer.

## Backend resource boundary

SDL GPU types are confined to the current backend implementation and its
private helpers. Public/general render headers, `BaseRenderer`, `Mesh`, and the
EditorViewport semantic contract expose no SDL GPU handles. This boundary does
not introduce `RenderDevice`, a generic graphics API, backend selection,
materials, textures, render threading, or a new GUI pipeline. See
`devdocs/CurrentArchitecture/RendererBackendBoundary.md` for the verified
ownership and leakage audit.

## Renderer technology decision checkpoint

This section is non-normative future guidance. Gargantuan should revisit its
renderer technology before the "competent lighting/renderer" roadmap work grows
into a mature material, asset, lighting, culling, batching, and post-processing
stack. The decision should be driven by a measured comparative prototype, not by
making the current SDL implementation permanent by default.

The candidate directions are:

1. Gargantuan owns engine and rendering semantics while Filament supplies most
   rendering technology.
2. Gargantuan owns engine semantics while Ogre-Next owns a disposable,
   persistent render-side scene projection.
3. Gargantuan owns both engine semantics and a renderer built on a lower-level
   API such as Diligent or SDL GPU.

The first investigation should introduce only the smallest internal backend
seam needed to compare one serious alternative, initially Filament, with the
current SDL path. It should not build three polished backends. Compare at least
material flexibility, instancing and batching, culling, lighting, large-scene
performance, platform support, integration cost, debugging, licensing, and
EditorHost compatibility. If rendering behavior proves to be a product
differentiator that an integrated renderer cannot express without distorting
Gargantuan's model, that evidence can justify owning more of the stack.

Every option must preserve the existing authority boundary:

```text
authoritative DataModel
    -> extracted or incrementally maintained render projection
    -> immutable publication
    -> renderer-owned scene and GPU resources
```

Any persistent render scene is a disposable `ObjectId`-indexed projection, not
game state. It must never become authoritative or retain live `Instance`
pointers. As scene scale makes full per-frame traversal, transform inversion,
sorting, and snapshot reconstruction materially expensive, evaluate an
incremental `RenderProjection` fed from committed changes. Publication to the
renderer must remain immutable even if its construction becomes incremental.

Renderer benchmarks must also separate GPU rendering from Studio viewport
presentation. GPU-to-CPU readback, pixel conversion, shared-memory transfer,
managed copies, and bitmap upload can dominate observed Studio frame time
independently of the renderer. Measure these stages separately. A shared GPU
texture may later become the preferred fast path, while the bounded RGB
shared-memory transport remains a portable fallback; adopting such a path
requires its own process-boundary and lifecycle review.
