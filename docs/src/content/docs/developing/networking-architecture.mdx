This document is the architecture decision record for Gargantuan's future game
networking. It refines the [future architecture](./future-architecture/) without
declaring an unfinished transport backend or public API spelling to be final.

**Status:** The boundaries and invariants in this document are accepted design
direction. Deterministic simulator validation confirmed the semantic delivery,
lifecycle, boundedness, and scheduler/transport split. Names marked as
candidates, binary layouts, real transport selection, and tuning values remain
provisional pending their respective implementation evidence.

**Implementation status:** The Attributes and Tags prerequisite, native
protocol-input hardening, backend-neutral pure contracts, deterministic
in-memory transport, simulator validation, and the scheduler semantic contract
are complete. The simulator exercises delivery and lifecycle semantics without
sockets, and a deterministic policy proof validates scheduler admission,
precedence, budgets, supersession, and flush behavior. The production scheduler,
real transport, and runtime phases below remain unfinished.

## Context

Gargantuan already has stable session object identity, a bounded `WireValue`
model, snapshots, an ordered `ChangeJournal`, a mutation gateway, and a frozen
runtime schema. Those are the right inputs for networking, but none of their
current debug or in-process representations should automatically become the
real-time game protocol.

Roblox networking libraries such as QuickNet, ByteNet, and Blink compensate for
the generic serialization and scheduling available above Roblox's engine. Their
transferable lessons are schema-driven codecs, generated or precomputed layouts,
validation, compact identifiers, batching, and explicit reliable/unreliable
delivery. Gargantuan owns the engine layer, so these should be normal native
behavior rather than a Luau optimization framework developers must add later.

## Decisions

### Three layers of state

Networking must preserve three distinct representations:

1. **Authoritative state** is the server-owned DataModel plus its committed
   `ChangeJournal`. It records what happened in the authoritative world.
2. **Replication intent** is a per-peer `ReplicationView` and a stream of
   `ReplicationOperation` values. It describes what a particular peer should
   know, after relevance, authority, coalescing, priority, and budget decisions.
3. **Wire delivery** is scheduling, encoding, packetization, and transport. It
   describes how and when bytes should reach the peer.

For example:

```text
Authoritative state: Position changed on Object 712
Replication intent:  Send Client A the latest transform for Object 712
Wire delivery:       Unreliable sequenced, priority 3, state sequence 5512
```

These layers must not collapse into one universal replication record. A journal
record can be irrelevant to a peer, several records can coalesce into one state
update, and one operation can be encoded differently as protocols evolve.

### Separate replication from application remotes

Engine replication and Luau remotes share connection management, codecs,
scheduling, congestion budgets, authentication, and transport primitives. They
do not share semantics.

```text
DataModel
    -> MutationGateway
    -> ChangeJournal
    -> ReplicationCoordinator
    -> ReplicationOperations
    -> NetworkScheduler
    -> IGameTransport

Luau remotes
    -> RemoteManager
    -> remote messages
    -> NetworkScheduler
    -> IGameTransport
```

Replication synchronizes authoritative state. Remotes carry explicit application
events or requests. Replication must not be implemented as hidden RemoteEvents,
and RemoteEvents must not become arbitrary DataModel mutation messages.

### Independent sequence domains

`ChangeJournal.Sequence` belongs only to authoritative source history. It is not
a packet number or a client replication cursor. A client can legitimately skip
server-only, irrelevant, coalesced, or lossy state without implying packet loss.

The architecture therefore reserves separate sequence domains:

| Domain | Purpose |
| --- | --- |
| `ChangeJournal.Sequence` | Ordered authoritative history within a DataModel scope |
| `ReplicationEpoch` | Identifies a peer's current baseline or snapshot generation |
| `ReliableReplicationSequence` | Orders reliable replication for one connection or logical stream |
| `RealtimeStateSequence` | Rejects stale state per object/component/state channel |
| `RemoteEventSequence` | Provides ordering or newest-wins semantics where the remote contract requires it |
| `RemoteFunction.RequestId` | Correlates one bounded request with its terminal result |

No gap in `ChangeJournal.Sequence` may be interpreted by a client as network
loss. Sequence widths, wrap behavior, stream granularity, and acknowledgement
formats are protocol design choices to settle with the simulated transport.

### Authoritative and replica lifecycles

Object lifecycle and replica visibility are different:

```text
Create / Destroy
    authoritative object lifecycle

Publish / Unpublish
    replica lifecycle for one peer
```

An object leaving a peer's interest set is unpublished, not destroyed. It may
later be republished with the same live authoritative identity. Wire-level names
such as spawn/despawn remain possible, but internal semantics must retain this
distinction so streaming never corrupts authoritative lifecycle history.

Each connection eventually owns a `ReplicationView` containing known and
relevant objects, active baselines, visibility, ownership, subscriptions, and
bandwidth state. Interest management lives above the journal and produces
publish, update, and unpublish intent per peer.

### Familiar remote semantics with stricter contracts

Gargantuan should preserve the familiar Roblox developer model while fixing
unsafe or underspecified behavior. The required semantic primitives are:

| Semantic primitive | Delivery | Ordering |
| --- | --- | --- |
| Reliable event | Delivered while the connection remains healthy; terminal connection failure is reported | Ordered within its declared logical channel |
| Unreliable event | Best effort; may be dropped or duplicated | Unordered |
| Unreliable sequenced event | Best effort; stale values are discarded | Newest accepted sequence wins within its state channel |
| Remote request | Reliable request/response | Correlated by request ID and always terminates |

`RemoteEvent`, `UnreliableRemoteEvent`,
`UnreliableSequencedRemoteEvent`, and `RemoteFunction` are preferred candidate
public names because they are understandable to Roblox developers. The exact
class surface remains provisional until the contracts are prototyped.

A remote request suspends only its calling Luau coroutine. Every request has a
finite deadline and terminates with a response, timeout, cancellation,
disconnect, or structured error. Server-to-client requests never wait
indefinitely on an untrusted client. The runtime enforces per-peer and per-remote
concurrency, byte, call-rate, decode-cost, and handler-cost budgets.

No implicit causal ordering is promised between a remote and replicated state
on another channel. When a remote requires a newly published object reference,
the reliable scheduler can encode an explicit dependency on the required
publish/baseline. It must not rely on incidental packet order.

### Reference visibility

Object references are encoded using stable wire identity and validated against
the sending and receiving scopes. A client reference to an object it is not
authorized to know is rejected before gameplay code runs.

A reliable server message that references an authorized but not-yet-materialized
object may wait behind the necessary publish/baseline dependency. An unreliable
message cannot wait indefinitely; it is dropped or rejected according to its
declared contract. The engine reports this outcome rather than silently replacing
an unresolved reference with nil.

### Schema-aware codecs

The frozen runtime schema is the source for type validation and precomputed game
wire layouts. A negotiated session can map stable `SchemaId`, class members,
enums, and remotes to compact connection-local indexes. Common indexes should be
compact without imposing a fixed 255-definition limit; varint identifiers are a
candidate encoding.

Hot replication can use property masks and typed encodings rather than repeating
class and property names. State may use an explicit network representation, such
as a quantized transform, without changing its native C++ or persistence format.
The codec must remain versioned, bounded, fuzzable, and independent from native
memory layout.

The existing JSON snapshot and journal DTOs remain appropriate for EditorHost,
debugging, and correctness tests. They are not the optimized multiplayer wire:

```text
ChangeJournal
    -> Studio/debug projection -> JSON WireCodec -> EditorHost IPC
    -> replication planning    -> binary GameCodec -> game transport
```

### Scheduling and traffic policy

A Luau call does not immediately create a network packet. The
`NetworkScheduler` batches small messages at explicit flush boundaries, packs
them within transport limits, assigns priorities and delivery policy, and
applies per-connection budgets.

Initial traffic classes should express needs rather than hard-code transport
lanes:

- control, handshake, acknowledgements, and disconnect;
- reliable structural replication and baselines;
- reliable application events and request responses;
- realtime sequenced state such as transforms and physics;
- ephemeral unreliable events; and
- low-priority background replication or asset coordination.

The final lane count and weights are transport tuning, not public semantics.
Reliable congestion produces bounded backpressure and eventually a structured
disconnect; it never grows an unlimited queue. Unreliable congestion preferentially
drops stale or low-priority work before encoding or transmission.

One unreliable application message must fit inside one negotiated transport
datagram. Gargantuan does not fragment unreliable application messages. An
oversized send fails with an actionable error telling the developer to reduce
the payload or select reliable delivery.

### Transport boundary

Gargantuan will not implement its own reliable UDP, congestion controller,
cryptography, retransmission, fragmentation, or path management. A
Gargantuan-owned `IGameTransport` boundary provides message-oriented connection
lifecycle, reliable and unreliable sends, polling, negotiated datagram limits,
statistics, authentication hooks, and structured disconnect reasons.

Code above this boundary cannot depend on backend types. Encryption does not by
itself authenticate a Gargantuan player or server; the handshake consumes a
short-lived session ticket or equivalent proof issued by the hosting/control
plane.

**Current preferred initial real-game transport candidate:** Valve
GameNetworkingSockets, because its message model, reliable/unreliable delivery,
prioritized lanes, diagnostics, and network simulation align with games. Final
backend selection is deferred until the simulated-transport contracts are
proven.

QUIC remains a serious candidate when standards interoperability, connection
migration, direct Go compatibility, or browser-adjacent deployment matters.
QUIC reliable streams require application message framing, while QUIC DATAGRAM
provides congestion-controlled unreliable delivery without retransmission.

### Game, platform, and editor planes

The low-latency game plane and the platform service plane are separate:

```text
Game plane
    Client <-> C++ game server
    replication, remotes, realtime state
    IGameTransport backend

Platform plane
    C++ game server <-> hosted services
    discovery, matchmaking, persistence, messaging, assets, telemetry
    mature typed service protocols such as HTTP/2 or gRPC
```

The hosting control plane returns an endpoint and authenticated join grant. It
does not normally proxy every gameplay packet. A future relay is a distinct
data-plane service rather than an accidental responsibility of the core node.

Local Studio keeps its EditorHost IPC, structured snapshots, and ordered journal
protocol. It does not switch to the game protocol merely because one exists.
Future collaborative editing may reuse transport and authentication foundations,
but uses an editor transaction protocol and waits for durable document identity,
undo, and conflict semantics.

## Simulated transport requirement

The first transport implementation is deterministic and in-memory. It can
control latency, jitter, loss, duplication, reordering, bandwidth, queue limits,
MTU, and disconnect timing from a seeded test configuration.

At minimum, tests must prove:

- reliable messages eventually arrive in contract order while connected;
- unreliable messages may disappear or duplicate without corrupting state;
- sequenced state never regresses after a newer sequence is accepted;
- every remote request terminates, including on disconnect and timeout;
- reliable queues and decoded work remain bounded;
- congestion drops stale unreliable work;
- replication can skip irrelevant journal entries and coalesce state;
- publish/unpublish never becomes authoritative create/destroy; and
- a journal sequence gap is never treated as packet loss.

The fake transport must test protocol behavior, not reproduce a chosen real
backend's API. The pre-backend validation checkpoint covers transport delivery,
lifecycle, bounds, statistics, and scheduler policy. Requirements that need a
`RemoteManager` or `ReplicationCoordinator`—remote request termination,
irrelevant journal filtering/coalescing, and publish/unpublish execution—remain
mandatory validation gates for those later layers and are exercised against the
simulator when those layers exist. They are not falsely claimed by the transport
alone.

### Validation checkpoint result

The simulator confirmed the accepted transport semantics without requiring an
architectural invariant change. It also established the boundary needed before
a real adapter:

```text
NetworkScheduler
    owns semantic admission, queues, selection, supersession, per-tick budgets,
    batching opportunities, transport submission, and scheduler statistics

IGameTransport
    owns delivery mechanics, transport resource limits, lifecycle, terminal
    outcomes, datagram availability, and transport statistics
```

`Submit` queues a validated `NetworkMessageIntent`; it does not immediately
send a packet. `Flush` is an explicit per-connection scheduling boundary that
makes eligible work available to the transport within a validated budget. It is
not a delivery acknowledgement. Reliable `WouldBlock` is observable temporary
backpressure, while hard reliable backlog exhaustion is structured and terminal.
Unreliable work may be dropped before submission, and newer unsent sequenced
state supersedes older state in the same existing channel.

The validation matrix and deterministic evidence are recorded in
`devdocs/CurrentArchitecture/NetworkSchedulerContract.md`. Real-backend evidence
is still required for backend-specific congestion behavior, diagnostics,
handshake integration, and tuning.

## Security and resource limits

Clients are hostile. Authentication happens before a peer can submit
DataModel-facing work. All decoded client intent passes schema/type validation,
scope and reference checks, capability and authority checks, contextual gameplay
validation, and the mutation gateway before affecting authoritative state.

Limits are negotiated downward from server policy and include packet and decoded
message bytes, strings, arrays/maps, nesting, arguments, remote rate, decode and
handler work, in-flight request count, reliable queued bytes, replication backlog,
baseline size, and per-tick send/receive budgets. Stale-sequence rejection occurs
before expensive decoding where the framing permits it.

Malformed input fails closed with structured diagnostics and connection policy.
Network decoders, handshake negotiation, reference handling, and connection
state machines require fuzzing and hostile corpus tests before opening a public
port.

## Implementation order

This checklist records implementation progress without changing the authority
of the accepted decisions above.

- [x] **Finish and review Attributes and Tags.** Confirm frozen-schema,
   serialization, journaling, Studio, and capability behavior.
- [x] **Harden protocol inputs.** Complete same-scope reference validation,
   hostile-input bounds and fuzzing, authenticated command-origin policy, and
   transaction/notification safe points.
- [x] **Define pure contracts.** Add backend-neutral delivery modes, connection
   state, traffic intent, limits, statistics, replication views/operations, and
   remote request outcomes without selecting GNS or opening sockets.
- [x] **Implement deterministic simulated transport.** Prove delivery, scheduling,
   backpressure, cancellation, and sequence-domain behavior under hostile
   conditions.
- [x] **Stop and validate.** Exercise the contracts, inspect metrics and failure
   behavior, and revise this ADR before committing to a real backend.
- [ ] **Select and implement one real transport adapter.** Add handshake,
   authentication hook, connection lifecycle, negotiated limits, and stats.
- [ ] **Add bounded Luau remotes.** Preserve familiar event/request ergonomics over
   the tested scheduler and transport semantics.
- [ ] **Add basic client replication.** Implement baseline plus reliable publish,
   update, reparent, attributes, and unpublish operations.
- [ ] **Add realtime replication when gameplay requires it.** Introduce sequenced
   transforms/physics, ownership leases, interpolation, and correction.
- [ ] **Add interest and streaming when world scale requires it.** Expand
    per-client views, priorities, relevance, and bandwidth policy.

Node integration for discovery and join tickets can proceed independently once
the handshake contract exists. Collaborative editing remains later work.

## Deferred decisions

The following are intentionally not fixed by this ADR:

- GNS versus QUIC or another mature real transport;
- exact public Instance class names and method spelling for remotes;
- exact binary field layout, compression, quantization, and varint scheme;
- sequence widths, wrap rules, acknowledgement layout, and channel granularity;
- scheduler tick rate, traffic lane count, weights, and default budgets;
- transport-specific certificate or key distribution;
- prediction, rollback, physics ownership, and reconciliation algorithms;
- interest rules and spatial data structures; and
- collaborative editing transport and conflict resolution.

These choices require measurements or later gameplay requirements. Implementations
may not bypass the accepted layer, authority, lifecycle, or boundedness decisions
while exploring them.

## Research basis

- [Roblox remote events and callbacks](https://create.roblox.com/docs/scripting/events/remote)
  documents the familiar reliable event, unreliable event, and yielding request model.
- [Roblox client/server boundary guidance](https://create.roblox.com/docs/scripting/security/client-server-boundary)
  reinforces server validation of every client-controlled input.
- [QuickNet](https://devforum.roblox.com/t/quicknet-v033-up-to-10x-faster-than-remoteevents-drop-in-networking-library/4624342/1),
  [ByteNet](https://ffrostfall.github.io/ByteNet/), and
  [Blink](https://1axen.github.io/blink/) demonstrate batching, typed schemas,
  compact buffer codecs, reliability selection, and generated protocols above Roblox.
- [GameNetworkingSockets](https://github.com/ValveSoftware/GameNetworkingSockets)
  provides a game-oriented candidate with message delivery, lanes, encryption,
  diagnostics, and network-condition simulation.
- [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000) and
  [RFC 9221](https://www.rfc-editor.org/rfc/rfc9221) define QUIC streams and QUIC
  unreliable datagrams as a standards-based alternative.
- [MsQuic API documentation](https://microsoft.github.io/msquic/msquicdocs/docs/API.html)
  describes a cross-platform native QUIC implementation candidate.
